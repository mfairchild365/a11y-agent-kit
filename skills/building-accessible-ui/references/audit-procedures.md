# Audit procedures

Test steps for the criteria auditors most often get wrong, so audits find the same issues each time. Open this file when you audit, and use an entry whenever its criterion is in play.

**These procedures are not the scope of the audit.** Audit against the whole checklist and every WCAG 2.2 A and AA criterion that applies. For an applicable criterion with no entry here, read its W3C Understanding document (`https://www.w3.org/WAI/WCAG22/Understanding/<slug>.html`), apply the boundaries it states, and name the criterion in your Checks line.

How to read an entry:

- **Fails when** and **Does not fail** state what the Understanding page says the criterion does and doesn't require. **Does not fail** is the field that prevents over-reporting: check it before you log anything.
- Text marked "Auditor guidance:" is practical advice that is not on the page.
- **Rate it** follows `audit-calibration.md`. "By impact" means no anchor applies: rate by what the user can't do.
- Where a build rule in another reference is stricter than the criterion (for example `reflow.md` asks for single-column stacking), this file follows the criterion, because an audit reports criterion failures.
- Each entry was drafted from its Understanding page and checked line by line against the page text. The review date is in its Source line. To change an entry, see `AUTHORING.md`.

### 1.1.1 Non-text Content (A)
- **Applies when:** any image, icon, SVG or other non-text content is presented to the user: status icons (error, warning, success, info), icon-only controls, informative images, charts. Auditor guidance: open this for every icon marked `aria-hidden`, `alt=""` or `role="presentation"`, and ask what it tells a sighted user.
- **Test:** 1. List each icon and image, and what it shows. 2. For each one hidden from assistive technology, decide whether it is pure decoration (the page: "serving only an aesthetic purpose, providing no information, and having no functionality"). 3. A status icon is not decoration when the adjacent text doesn't state the same thing. Read the message text: does it say "Error", "Warning" or "Success" (or equivalent) in words? Text that only implies the type doesn't count (maintainer decision, C-018). 4. If it carries information, check it has a text alternative that serves the equivalent purpose, or that the text states the same information. 5. Controls: an icon-only control needs a name that describes its purpose (see 4.1.2). 6. Check the alternative is updated when the icon changes (F20). Automation: axe `image-alt`, `svg-img-alt`, `role-img-alt`, `input-image-alt` find missing alternatives. No rule can tell whether a hidden icon is decorative, so steps 2 and 3 need a human reading.
- **Fails when:** Non-text content that conveys information has no text alternative serving the equivalent purpose. Listed failures: F3 (information only in CSS background images), F13 (alternative omits what color conveys), F20, F30, F65 (missing alternative), F67, F71, F72. Auditor guidance: an informative icon hidden with `aria-hidden` or `alt=""` is the same failure as F65.
- **Does not fail:** Pure decoration, visual formatting, or content not presented to users, when it is implemented so assistive technology ignores it (F38 fails when it isn't; F39 fails when it gets a non-empty alternative). An icon next to text that states the same information in words: the icon is redundant, and hiding it is correct (the page's H2 and G196 techniques cover a text alternative on one item that describes the group). A decorative icon with an alternative is a Best practice miss at most.
- **Rate it:** By impact. An informative status icon with no alternative and no stating text: the user loses the type of the message (error or success), so it is never Minor. Severity isn't on the confirmed anchors; say so in Why this severity.
- **Source:** https://www.w3.org/WAI/WCAG22/Understanding/non-text-content.html (read 2026-10-09).

### 1.3.1 Info and Relationships (A)
- **Applies when:** any page where the look of the content shows structure or a relationship: headings, lists, table rows and columns, groups of form fields, labels beside controls, emphasized or special text, links, and regions. The page says sighted users read these from visual cues (a larger bold font, a bullet, rows and columns, fields placed together), and the same information must be available to a screen reader or a user style sheet. Auditor guidance: this is the criterion to open for any "it looks like an X, but it isn't marked up as one" finding.
- **Test:** 1. Read the accessibility tree (Playwright `locator.ariaSnapshot()`) and the rendered page side by side, and look for each visual structure in turn. 2. **Headings:** find text that looks like a heading (larger, bolder, or set apart from the text around it) and check that it is `<h1>`-`<h6>` or `role="heading"` with `aria-level` (H42 check 1). A toast or snackbar title counts: it must be a heading too. Then check the reverse: heading markup on text that is not a heading, such as a pull quote or a bold label inside a paragraph (H42 check 2). Check that each level puts the heading in the right place in the outline (see Does not fail for skipped levels). 3. **Lists:** find content that looks like a list (bullets, numbers, a stack of short items, a group of links) and check it is `ul`, `ol` or `dl`, not asterisks, dashes or `<br>` between items (H48). 4. **Tables:** find content arranged in rows and columns where each cell relates to a row and a column header. It should be a `table` with `th` cells (H51), and with `scope` or `headers`/`id` when the headers are not in the first row or column, or there is more than one level of headers (H63, H43, F91). Check that a `headers` attribute lists the `id` of every header the cell has and that each id exists and is unique (F90). Check that a `table` used only for layout has no `th`, `caption`, non-empty `summary`, `headers` or `scope` (F46, F43), and that a `pre` block or spaces and tabs are not used to line up columns (F48, F33, F34). 5. **Form groups and labels:** check that each control's label is programmatically associated (H44), and that related controls whose individual labels don't describe the group are in a `fieldset` with a `legend` as its first child, or a `role="group"` or `role="radiogroup"` with an accessible name (H71, ARIA17). 6. **Special text and links:** check that emphasis the look conveys (bold, italic, a different font for a term) is also in markup (`strong`, `em`, `mark`, H49) or in text, and that anything that looks and acts like a link is an `a` with an `href`, not a `span` or `div` with a click handler (F42). 7. **Roles that remove semantics:** check that no `role="presentation"` or `role="none"` sits on content that conveys structure, such as a data table or a list (F92). Check that structural markup is not used only for its look, such as a `blockquote` for indentation or a list for layout (F43). 8. **Information shown only by presentation:** find any information shown only by size, weight, position or an icon. It must also be in text or markup (G117, F2). Color values need not be exposed (Note on the page); information shown only by color is a 1.4.1 question. 9. Run axe and read the results by rule. Rules tagged `wcag131` in axe 4.13: `list`, `listitem`, `definition-list`, `dlitem`, `td-headers-attr`, `th-has-data-cells`, `aria-required-parent`, `aria-required-children`, and the experimental `p-as-heading`, `td-has-header` and `table-fake-caption` (enable experimental rules explicitly). Check the installed version's tags. The Understanding page also lists ACT rules: "Headers attribute specified on a cell refers to cells in the same table element", "Table header cell has assigned cells", and the ARIA required context, owned elements and ID reference rules. Automation cannot tell whether text is meant as a heading, whether a grid of content is tabular, or whether markup represents a real relationship in the content, so steps 2 to 8 need a human reading of the page.
- **Fails when:** Information, structure or relationships that the presentation conveys are not in the markup or in text (the SC text). The page's failure techniques: F2 (a change in text presentation conveys information with no matching markup or text, which includes images of text carrying structure); F33 and F34 (white space used to make columns or tables in plain text); F42 (an emulated link: a script-made link whose programmatic role is not "link" fails 1.3.1 and 4.1.2, and one that can't be activated by keyboard fails 2.1.1 and 2.1.3); F43 (structural markup that states a relationship that is not in the content, so the element's meaning exposed to assistive technology is wrong for the content); F46 (`th`, `caption` or a non-empty `summary` in a layout table; `headers` and `scope` in one would fail too); F48 (`pre` used for tabular data); F90 (`headers` and `id` that don't associate the right cells); F91 (a data table whose headers are not programmatically determinable by `th`, `scope`, `headers`/`id`, or the ARIA `rowheader` and `columnheader` roles); F92 (`role="presentation"` on content whose markup conveys information or relationships); F111 (a control with visible label text and no accessible name fails 1.3.1, 2.5.3 and 4.1.2). H42 is the reference test for headings: heading markup is used where the content is a heading, with the appropriate level, and is not used where the content is not a heading.
- **Does not fail:** A page whose structure is in the markup or in text, even when it uses none of the page's techniques (they are examples; "there may be other ways"). Color values: it is not required that they be programmatically determined (Note on the page; 1.4.1 covers color). A `fieldset` and `legend` for radio buttons or checkboxes whose individual labels are clear and distinct on their own (H71: "H44 is sufficient in this case"); a group description is needed only where the labels don't give it. A layout table that has none of the markup F46 lists. `role="presentation"` or `role="none"` on an element whose semantics don't match the content, since it hides the wrong meaning (F43 note). A simple data table with `th` in the first row or column and no `scope` (H63 note: "it is sufficient to simply use the th elements without scope"). Auditor guidance, confirmed by the maintainer on 2026-10-08: **a skipped heading level (an `h2` followed by an `h4`) is a Best practice, not a failure**, because the page asks for properly nested headings only as advisory technique G141. It becomes a 1.3.1 failure (H42 check 1, the level is not appropriate) when the levels make other headings appear in the wrong place in the outline, for example a heading that is a sibling of an earlier section but is given a deeper level, so that it reads as that section's child. Auditor guidance, confirmed by the maintainer on 2026-10-09 (C-020): **a `section` or `role="region"` that has a visible heading and also an `aria-label` or `aria-labelledby` is a Best practice, not a failure.** It makes a landmark that is announced next to the heading, a redundant announcement. Look for it in step 2. A name that tells apart two landmarks of the same kind is needed and isn't logged. Auditor guidance, not on the page: a missing landmark or a page with no `h1` is not a 1.3.1 failure on its own (H101 and ARIA11 are sufficient techniques, not requirements). Report it as a Best practice, or under 2.4.1 and 2.4.6 if a blocking problem follows.
- **Rate it:** Text that looks like a heading but is a `<p>`, `<div>` or `<span>`: **Critical** (calibration A). Otherwise by impact, since no other anchor applies: what can a screen reader user not find, scan or get from the content? Name which structure is missing in Why this severity. A heading level that puts a heading in the wrong place in the outline is rated by that impact. A control with visible label text and no accessible name is also Critical under 4.1.2 (file it there, and under 2.5.3 as a separate issue, per calibration B). A skipped level alone gets the label "Best practice" and no severity. One success criterion per issue: an emulated link also fails 2.1.1 and 4.1.2, so log those separately and cross-reference them.
- **Source:** https://www.w3.org/WAI/WCAG22/Understanding/info-and-relationships.html and the technique pages F2, F42, F43, F46, F48, F90, F91, F92, H42, H43, H48, H51, H63, H71 and G141 (read 2026-10-08).

### 1.4.3 Contrast (Minimum) (AA)
- **Applies when:** The page has any rendered text, including placeholder text, text shown on pointer hover or keyboard focus (tooltips, popups), and images of text. Auditor guidance: check every state (default, hover, focus, active, visited, selected, error).
- **Test:** 1. Run axe `color-contrast` in each state (hover and focus need the state forced: Playwright `hover()` / `focus()`, then re-run axe). 2. For each text/background pair, read the foreground and background colors from the computed styles or the stylesheet, not from a screenshot. 3. Compute the ratio with the WCAG formula (L1 + 0.05) / (L2 + 0.05). Do not round. 4. Decide the threshold: 4.5:1, or 3:1 if the text is large-scale (at least 18pt, or at least 14pt bold; the page gives these as approximately 24px and 18.5px). 5. Auditor guidance: for text over a gradient or image, measure the least contrasting area behind the text. 6. Check placeholder text and tooltip text too. ACT rule: "Text has minimum contrast". Auditor guidance: automation cannot see text over images or gradients (axe reports "incomplete"), text with alpha or opacity, pseudo-element text, text in images, states axe did not trigger, or whether text is decorative.
- **Fails when:** The computed ratio is below 4.5:1 for normal text, or below 3:1 for large-scale text. Do not round: 4.499:1 does not meet 4.5:1. Also fails when a text color is set without a background color, or the reverse (F24). Also fails for a background image that does not give enough contrast with the text (F83).
- **Does not fail:** Text in an inactive component, such as a disabled control. Pure decoration (words that could be rearranged or substituted without changing meaning). Text that is not visible to anyone. Text that is part of a picture with significant other visual content. Text in a logo or brand name. Incidental text, such as a street sign in a photo. Brand guidelines do not exempt other text. Heavily stylized text that acts as a graphic, and text characters used as symbols, are judged under 1.4.11, not here. Judge the colors from the user agent or the markup and stylesheets, not how anti-aliasing renders the text on screen. A border around a letter can add contrast.
- **Rate it:** Critical (text contrast failure in any state, including hover and focus).
- **Source:** https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html (read 2026-10-07).

### 1.4.10 Reflow (AA)
- **Applies when:** any page or view with text, controls, or media that could be wider than a narrow viewport. Content that scrolls vertically (text in a language written horizontally, such as English) is tested at a width of 320 CSS px. The 256 CSS px height applies only to content designed to scroll horizontally, such as text in a language written vertically (for example vertical traditional Chinese or Japanese). Don't test an ordinary page at 256 px.
- **Test:** 1) Open the page at a 320 CSS px wide viewport (Playwright `setViewportSize({width:320,height:800})`), or at 1280 px wide with browser zoom at 400%. The page says these are equivalent. 2) Auditor guidance: compare `document.documentElement.scrollWidth` to `clientWidth`. If wider, find the elements that stick out and decide if each needs two-dimensional layout. 3) Read every block of text. The page's concern is users being forced to scroll back-and-forth to read line by line, so check whether reading a block (several lines) needs sideways scrolling. One overflowing line does not fail (see Does not fail). 4) Open each state (menus, dialogs, accordions, tabs, validation errors) and repeat. 5) Tab through. Every control and every piece of information must still be reachable, not clipped or hidden. 6) Only for content designed to scroll horizontally (text in a vertical writing mode), repeat at a 256 px tall viewport (1024 px tall at 400% zoom). Skip this for ordinary pages. 7) Check excepted content (table, map, video): other content on the page must still reflow. Automation: the only ACT rule on the page is "Meta viewport allows for zoom". No axe rule or ACT rule tests 320 px overflow. axe `meta-viewport` is tagged for 1.4.4 Resize Text, not Reflow, so do not use it as the Reflow check. Loss of content, what needs two-dimensional layout, and `overflow: hidden` clipping need human judgement.
- **Fails when:** reading non-excepted content needs scrolling in two dimensions: sideways back-and-forth to read lines of text at 320 CSS px (vertically scrolling content), or vertical back-and-forth at 256 CSS px (content designed to scroll horizontally). Or information or functionality is lost, and no exception applies. Several stacked lines that each run past the edge fail, because the user scrolls back to the start of every line. Failure F102 is content disappearing and not being available when content has reflowed. Also fails: a table with no scrollable container of its own, so that the paragraphs after it need two-dimensional scrolling. A carousel panel that does not fit in 320 px. Headings, search fields, or pagination next to an excepted table or map that do not fit (they are not excepted). Individual table or grid cells that do not fit, unless the cell content itself needs two-dimensional layout.
- **Does not fail:** a single line that runs past the edge, such as one long label, heading or button text, because the user isn't forced to scroll back-and-forth to read line by line. Auditor guidance, confirmed by the maintainer: the page's Intent describes that back-and-forth reading and doesn't address a lone overflowing line, so treat it as a Best practice (wrap it), not a failure. Parts that require two-dimensional layout for usage or meaning. The page lists: images required for understanding (maps, diagrams), video, games, presentations, data tables (not individual cells), and interfaces where toolbars must stay in view while content is edited. It also discusses grids such as a program guide, code or ASCII art where layout carries meaning, a two-column diff view (each column fits 320 px), carousels (each panel fits 320 px), and a rich text document with its own fixed size. A page-level horizontal scrollbar is fine if it comes only from excepted content and all non-excepted content needs scrolling in one direction. Not required: stacking everything in one column, scrolling in one direction only, or enlarging text. Adjusting or relocating content is not loss if users can still access it. Navigation behind a More menu or a hamburger button is fine when all information and functionality stay available. Truncated text passes if a link or control reveals the full text. If 200% zoom gives a viewport smaller than the Reflow sizes, two-dimensional scrolling there is not a Reflow failure. Devices are not required to support 320 px or 256 px.
- **Rate it:** Moderate for a reflow failure at 320 px. If a control becomes unreachable or inoperable, rate by impact (keyboard-inoperable = Critical at minimum, Blocker if no other way).
- **Source:** https://www.w3.org/WAI/WCAG22/Understanding/reflow.html (read 2026-10-07).

### 1.4.11 Non-text Contrast (AA)
- **Applies when:** A control's identity or state depends on a non-text visual cue: the border of a text input with no other cue, a checkbox square, a tick or radio dot, a selected-state indicator, an icon with no text, an author-styled focus indicator. Also applies to graphics where parts are needed to understand the content (chart lines, meaningful icons).
- **Test:** 1. List each control and ask: what non-text visual tells the user the control exists, and what shows its state? 2. If the control has visible content (such as text or a sufficiently contrasting icon) that identifies it, its border is not required. It still needs a sufficiently contrasting focus indicator. 3. For each required cue, read the cue color and the adjacent colors from computed styles in every state (default, hover, focus, checked, selected). 4. Compute the ratio and compare to 3:1 unrounded. 5. Tab to each control and check the focus indicator against the adjacent colors, only if the author changed the default. 6. For graphics, test the least contrasting area. If that area is below 3:1, assume it is invisible. If the graphic is still understandable, it passes. No axe rule and no ACT rule covers this criterion, and the page lists no test rules. Auditor guidance: axe `color-contrast` checks text, not borders or icons. Automation cannot see which cues are required, adjacent colors behind images or gradients, or whether a graphic is understandable.
- **Fails when:** A cue that is required to identify the control or its state has a ratio below 3:1 against the adjacent colors. Do not round: 2.999:1 does not meet 3:1. Examples from the page: a checkbox border #9D9D9D on white is 2.7:1; a link whose custom underline is the only way to identify it and contrasts less than 3:1; an author-styled focus indicator below 3:1 with its adjacent colors (the page's example is #AAA on white, 2.3:1). Also fails when author CSS styles outlines and borders so the focus indicator is removed or not visible (F78).
- **Does not fail:** A control with no visual boundary when its visible content identifies it: the page says this criterion does not require a visual boundary indicating the hit area. A disabled (inactive) control. A component whose appearance is set by the browser and not modified by the author, including the default focus style (it must still be visible). Author-supplied hover treatments, which the page treats as supplemental and not required to identify the hover state. State color changes that do not appear next to each other, as long as the component does not lose contrast with its adjacent colors. Logos. Graphics where a particular presentation is essential. Graphics that are decorative, or that have visible text giving the same information. Text within a graphic is judged by 1.4.3, not here.
- **Rate it:** Critical when the element is required to identify the control or its state (sole visual cue, meaningful icon without text, state indicator, author-styled focus indicator). Any other 1.4.11 failure is Moderate at minimum, never Minor (C-016). A cue that isn't required is not a failure. Auditor guidance: a low-contrast border on a control that already has a visible text label is at most a best practice, which has a label and no severity.
- **Source:** https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html (read 2026-10-07).

### 1.4.12 Text Spacing (AA)
- **Applies when:** text in markup languages that support these style properties (HTML/CSS qualifies): body text, headings, labels, buttons, tooltips, menus, error text, fixed-height or fixed-width containers, truncated text. The page says this SC does not currently apply to PDF. Video captions embedded in video frames and images of text are not expected to adapt, and canvas text counts as images of text.
- **Test:** 1) Load the page. 2) Inject a stylesheet with `!important` on all elements: `line-height: 1.5`, `letter-spacing: 0.12em`, `word-spacing: 0.16em`, and `margin-bottom: 2em` on `p` (use `page.addStyleTag`). The page gives the multipliers of font size; the CSS above is auditor guidance. Change no other style property. 3) Look at every state: open menus, dialogs, tooltips, tabs, errors. 4) Look for text cut off at the bottom or end, text overlapping other content, and controls whose label is clipped or pushed out. 5) Auditor guidance: tab through and activate controls to confirm they still work. 6) Check anything with an ellipsis: the full text must be revealed on focus or activation, or on a linked page. Text that was not truncated before but is now, with no way to reveal it, fails. Automation: the page lists ACT rules "Important letter spacing in style attributes is wide enough", "Important line height in style attributes is wide enough", and "Important word spacing in style attributes is wide enough". axe `avoid-inline-spacing` is the matching axe check (tagged wcag1412). Auditor guidance: these checks look at `!important` spacing in style attributes only. No automated rule sees clipping or overlap after the override.
- **Fails when:** after line height is set to at least 1.5 times the font size, spacing after paragraphs to at least 2 times, letter spacing to at least 0.12 times, and word spacing to at least 0.16 times, content or functionality is lost, text is clipped, or text overlaps other content (failure F104). Text truncated by the spacing change with no way to reveal it fails. Auditor guidance: inline `!important` spacing narrower than these values blocks the user override; the three ACT rules above test for it.
- **Does not fail:** authors do not have to use these values or provide a way to set them. A user agent or platform that gives users no way to set spacing is not a failure. Content does not fail if a user's extension or bookmarklet sets the properties wrongly, provided the content is not actively and purposely preventing the properties from being added. Languages and scripts that do not use one or more of these properties need only the properties that exist (for example, word spacing had no effect in Japanese). Ellipsis caused by the override is fine if the text is still available on focus, on activation, or on a linked page. Auditor guidance: text that wraps or grows taller without cut-off or overlap is fine. Images of text and captions embedded in video frames are not expected to adapt.
- **Rate it:** by impact. Hidden or unusable controls: rate as an inoperable control (keyboard-inoperable = Critical at minimum, Blocker if no other way). Lost information: by impact. Cosmetic overlap that stays readable: Minor, by impact.
- **Source:** https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html (read 2026-10-07).

### 1.4.13 Content on Hover or Focus (AA)
- **Applies when:** Pointer hover or keyboard focus makes additional content appear and then disappear, and the author controls how it looks: custom tooltips, sub-menus, other non-modal popups. Does not apply to content whose presentation is controlled by the user agent and not modified by the author (the HTML `title` tooltip), to modal dialogs, or to hidden components made visible on focus that present no additional content, such as skip links.
- **Test:** 1. Find each trigger that shows extra content on hover or focus. 2. Dismissible: show the content by hover, then by focus. Use a mechanism that does not move pointer or focus, usually the Escape key. The content must close. 3. Hoverable (only if hover can trigger the content): hover the trigger, then move the pointer onto the new content. It must stay visible. Auditor guidance: do this slowly, and across any gap between trigger and content. 4. Persistent: leave the pointer and focus in place. The content must stay until the trigger is removed, the user dismisses it, or the information is no longer valid. 5. Auditor guidance: check the content is still there after a delay, not just after a moment. 6. Auditor guidance: check that focus shows the same content as hover. The page says hover-triggered content should also be triggerable by focus, and points to 2.1.1 for that. No axe rule and no ACT rule covers this criterion, and the page lists no test rules. Automation cannot see these behaviors. Test by hand, or script `hover()`, `keyboard.press('Escape')`, and pointer moves in Playwright.
- **Fails when:** The extra content cannot be dismissed without moving pointer hover or keyboard focus, and it is not an input error and does not leave other content unobscured (see Does not fail). Or content shown on hover cannot be hovered: the pointer cannot move over it without it disappearing (F95). Or the content disappears before the hover or focus trigger is removed, the user dismisses it, or its information is no longer valid. Auditor guidance: a timer that hides the content is an example. The page lists the dismissible and persistent failures as potential future techniques with no ids.
- **Does not fail:** Dismissal is not required when the content communicates an input error. Dismissal is not required when the content does not replace or obscure other meaningful content (including the trigger): for example, it appears only over white space or purely decorative content. Escape is an example mechanism (the page says "such as pressing the Esc key"), not the only allowed one. Content that disappears when the user removes hover or focus from the trigger and the additional content is allowed. Content controlled by the user agent and not modified by the author, such as the `title` attribute tooltip, is out of scope. Modal dialogs are out of scope. Auditor guidance: content opened by click or activation (toggletip, disclosure) is not triggered by hover or focus, so judge it under other criteria.
- **Rate it:** By impact. (The skill's calibration example: a hover-only tooltip on an element that cannot take focus is two issues, 2.1.1 Critical and 1.4.13 Moderate.)
- **Source:** https://www.w3.org/WAI/WCAG22/Understanding/content-on-hover-or-focus.html (read 2026-10-07).

### 2.1.1 Keyboard (A)
- **Applies when:** The UI has any function a user can do with a mouse, touch, or gesture: buttons, custom widgets, menus, drag and drop, sliders, scrollable regions, iframes with controls, hover or click-only reveals.
- **Test:** 1. Put the mouse away. Press Tab and Shift+Tab through the whole flow. 2. Complete every function by keyboard only: Enter or Space on buttons and links, arrow keys inside composite widgets, Escape to close overlays. 3. Exercise each state: open menus, dialogs, disclosures, error states, hover-only reveals. 4. For drag and drop, resize, and sliders, look for a keyboard way to reach the same result. 5. Check that scrollable regions and iframes with controls can be reached by Tab or hold a focusable child. 6. For a custom control built on a div or span, confirm it gets focus and can be activated by keyboard. Automation: two ACT rules are listed: "Scrollable content can be reached with sequential focus navigation" and "Iframe with interactive elements is not excluded from tab-order". Auditor guidance: the axe rules `scrollable-region-focusable` and `frame-focusable-content` cover the same two cases (this mapping is not on the page). No automated rule sees click handlers on non-focusable elements, drag-only functions, or broken key handlers.
- **Fails when:** A function can be done only with a pointer, touch, or gesture, and no keyboard path gives the same or a comparable outcome. Also: a function needs specific timing for individual keystrokes; script removes focus on receipt (F55); only pointing-device-specific event handlers are used for a function (F54); a fake link built to emulate a link cannot be operated (F42). MouseKeys or another keyboard-operated mouse emulator does not count as keyboard operation.
- **Does not fail:** A visible mouse or touch control that is not keyboard focusable, when keyboard users can get the same or a comparable outcome another way. Example: a submit button that cannot take focus, where Enter in the text input submits the search. A separate keyboard mode of operation. Mouse or other input offered in addition to the keyboard. Functions whose input depends on the path of movement, not just the endpoints (free hand drawing, watercolor painting, a model helicopter flight simulator). Drag and drop where the path to the destination is not relevant is not exempt: it needs a keyboard way (for example cut and paste, or form controls). Resizing windows, drawing straight lines, and regular geometric shapes are not path dependent. A custom button that reacts only to Enter, not Space, still satisfies this SC. Auditor guidance: report the missing Space key as a best practice, with no severity.
- **Rate it:** Critical at minimum; Blocker if there is no other way to do the function. An unnamed focusable control is a separate Critical finding.
- **Source:** https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html (read 2026-10-07).

### 2.2.1 Timing Adjustable (A)
- **Applies when:** the content sets a time limit: an auto-dismissing snackbar or toast, a session timeout, a timed redirect. Auto-advancing carousels fall under 2.2.2. Auditor guidance: find timers with `setTimeout` and `setInterval` that remove or hide content or end a task.
- **Test:** 1. Trigger each message and time how long it stays (the live-region probe reports the dwell). 2. Check for one of the three options: the user can turn the limit off, adjust it to at least ten times the default, or is warned and given at least 20 seconds to extend it with a simple action. 3. Otherwise check for an alternative that doesn't rely on the timer: can the user get the same message again (a notification inbox or history, or the same information elsewhere on the page)? 4. Ask whether the message is actionable (has an Undo or a link) or important (an error, something to fix). 5. Check the exceptions below. Automation: none. No axe or ACT rule tests a timer.
- **Fails when:** A time limit sets how long content shows or a task can last, and none of turn off, adjust, extend applies, and no exception applies. The page lists failures for meta redirect and refresh (F40, F41, F58). On toast messages the page says a timed message needs no adjustment "if there is an alternative that does not rely on a timer" (its example: the user can find new email in the Inbox); otherwise "each message would need to meet this success criterion".
- **Does not fail:** A limit longer than 20 hours. A required part of a real-time event with no alternative. A limit that is essential, where extending it would invalidate the activity. A message the user can get again another way (inbox, history, an on-page status). Auditor guidance, confirmed by the maintainer on 2026-10-09 (C-017), not on the page: **pause on hover or focus is a good fix but doesn't settle the criterion alone**, because users may not get their pointer or focus into the message in time. Say so in the suggested fix.
- **Rate it:** By impact; severity isn't on the confirmed anchors. A timed message that is actionable or important is rated higher than a passing confirmation. The suggested fix names, in order: don't auto-dismiss actionable or important messages; let users re-open dismissed messages (inbox or history); and, as a supplement, pause on hover and focus.
- **Source:** https://www.w3.org/WAI/WCAG22/Understanding/timing-adjustable.html (read 2026-10-09).

### 2.4.7 Focus Visible (AA)
- **Applies when:** Any element that can receive keyboard focus: links, buttons, inputs, custom widgets, items inside composite widgets, elements inside modals and overlays, skip links.
- **Test:** 1. Tab and Shift+Tab through every focusable element; arrow through each composite widget. 2. At each stop, confirm something visibly shows which element has focus. 3. Repeat in each state: modal open, menu open, error state, dark mode, forced colors if supported. 4. Stay on one element: the indicator must remain visible as long as focus stays. 5. Auditor guidance: search CSS for `outline: none` or `outline: 0` without a replacement, and for script that blurs on focus. 6. Auditor guidance: if the indicator is author-styled, measure its contrast against adjacent colors (3:1 comes from 1.4.11, see contrast.md). Automation: one ACT rule is listed, "Element in sequential focus order has visible focus". No axe rule exists for this SC. Auditor guidance: automation cannot reliably judge whether an indicator is visible, so a keyboard walk is required.
- **Fails when:** A focusable element shows no visible focus indicator in keyboard use (F78: styling outlines and borders so the indicator is removed or not visible; F55: script removes focus when focus is received). Or the indicator disappears while the element still has focus: when the focus indicator is shown, it must remain visible. Or an author-styled indicator, which is non-text content, fails 1.4.11 Non-text Contrast; the page says focus indicators are subject to it. Auditor guidance: apply the 3:1 value from 1.4.11.
- **Does not fail:** The SC does not specify the form of the indicator; size and shape guidance belongs to 2.4.13 (AAA), so do not fail for those here. A user agent that does not always show an indicator, or shows it only when the keyboard is used, is accounted for by the SC wording about a mode of operation: the author needs at least one mode where focus is visible. A focus indicator for mouse or pointer users is a best practice, not a requirement. Auditor guidance: the page lists G165 ("Using the default focus indicator for the platform so that high visibility default focus indicators will carry over") and G149 as sufficient techniques, so treat an unmodified browser default indicator as passing; the page has no sentence saying so outright.
- **Rate it:** A missing indicator = by impact (Critical when users lose their place on a main path). An author-styled indicator that fails 3:1 = Critical (non-text contrast failure on the element that identifies the focused state).
- **Source:** https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html (read 2026-10-07).

### 2.4.11 Focus Not Obscured (Minimum) (AA)
- **Applies when:** Author-created content can overlap the page while a control has focus: sticky headers or footers, cookie banners, non-modal dialogs, chat widgets, floating toolbars, notification bars.
- **Test:** 1. Load at desktop width with the overlay content showing. Auditor guidance: repeat at 320 CSS px wide, where sticky layers often cover more. 2. Tab forward through the whole page, then Shift+Tab back. 3. At each stop, check that the focused component is not entirely hidden by sticky or floating content. Auditor guidance: in Playwright, compare the focused element's bounding box with `document.elementsFromPoint` at its corners and center, or take a screenshot. 4. Repeat with a non-modal banner, chat window, or dialog open. 5. Check for CSS scroll-padding (technique C43) on the scroll container. Automation: the page has no Test Rules section, so no ACT rule is listed. No axe rule exists for this SC. Auditor guidance: automation cannot see overlap well, so a keyboard walk is required.
- **Fails when:** The component with focus is entirely hidden by author-created content (F110: a sticky footer or header completely hiding focused elements). A sticky cookie banner or notification fails if it entirely obscures the focused component. A dialog-like overlay that does not take focus and does not constrain interaction or dismiss itself on loss of focus is at risk of failing where it can cover focusable items. Partly hidden is allowed at AA.
- **Does not fail:** A focused component that is only partially obscured. Content opened by the user that covers the focused component, when the user can reveal the component without advancing keyboard focus (for example Escape or scrolling). Movable content in a configurable interface: only its initial position is tested. A properly constructed modal dialog always passes. A sticky header or footer when the page scrolls so the focused item is not completely obscured. Non-persistent disclosures such as menus, select lists, date pickers, and tooltips. A fully obscured focus indicator on a visible component is judged by 2.4.7 (it would likely fail there), because this SC evaluates the component, not the indicator.
- **Rate it:** By impact. Auditor guidance: entirely hidden focus on a required control = Critical; on a rarely used control = Moderate.
- **Source:** https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html (read 2026-10-07).

### 2.5.3 Label in Name (A)
- **Applies when:** A user interface component has a visible label made of text or images of text: button text, link text, text beside an input or checkbox, text on a tab or menu item. It matters most when `aria-label` or `aria-labelledby` is set, because both override the visible text in the name calculation.
- **Test:** 1. List each control with a visible text label and compute its accessible name (Playwright `locator.ariaSnapshot()` or the DevTools Accessibility pane). 2. Compare the name to the visible label, ignoring case and most punctuation. 3. Check that the name contains the visible label text. Auditor guidance: also check each state that changes the label (toggled, loading, expanded). 4. Check that the label words are in the same order and have no extra words between them. 5. Run axe rule `label-content-name-mismatch` (experimental, off by default, so enable it explicitly). The page's Test Rules section lists the ACT rules "Visible label is part of accessible name" and "Form field has non-empty accessible name". Automation cannot decide which text is the label for a control or what counts as symbolic text. Auditor guidance: confirm with voice control by saying the visible label, as in "move to Password".
- **Fails when:** The name does not contain the text that is presented visually (the SC text). Failures listed on the page: F96 (name does not contain the visible label text) and F111 (control with visible label text but no accessible name). Two more are listed as potential future techniques: the name has the label words in a different order, and the name has other words interspersed in the label.
- **Does not fail:** No visible text label exists, for example an icon with no accompanying text; the page says the SC does not apply. Differences in capitalization and most punctuation: a name of "first name" is equivalent to "First Name:". A name that starts with the label and adds more: "Search for a value" for "Search". Text used as a symbol and not as human language, such as "B", "I", "ABC" on editor icons or ">" drawn as an arrow; the name should be the function. Math expressions can be labels, for example "A>B"; leave the formula as shown. Text in parentheses may be left out of the name, but important context such as "required" must then be exposed some other way. Headings, instructions, and group labels are not normally treated as the label. Matching case and putting the label at the start of the name are best practices, not requirements. Placeholder text is not an appropriate means of providing a label, but when no other nearby text exists it may still be a candidate for the label, so do not exempt it.
- **Rate it:** Moderate. A control with visible label text and no accessible name at all is also an unnamed control, so rate it Critical under 4.1.2 (F111 fails 1.3.1, 2.5.3, and 4.1.2). A best-practice miss (label not first, case differs) gets a label and no severity.
- **Source:** https://www.w3.org/WAI/WCAG22/Understanding/label-in-name.html (read 2026-10-07).

### 2.5.8 Target Size (Minimum) (AA)
- **Applies when:** any target for pointer input (a region that accepts a pointer action): buttons, icon buttons, checkboxes, radios, links, menu items, close buttons, tabs, table row actions, tags with remove buttons. Sliders, color pickers with a gradient, and editable areas where you position the cursor count as one target.
- **Test:** 1) List every focusable or clickable target on the page and in each state (menu open, dialog open, error shown). 2) For each, read the box that accepts pointer actions: `getBoundingClientRect()` on the element, including padding that is part of the clickable area. Do not use zoom: the requirement does not depend on zoom. 3) If a 24 by 24 CSS px square, aligned to the page axes, can be drawn fully inside the target, it passes. Rounded corners or clipping can make a target undersized even when its bounding box is 24 by 24 or larger. 4) If it is smaller, centre a 24 px diameter circle on the centre of its bounding box. Do the same for each neighbouring undersized target. 5) It passes if no circle intersects another target or another undersized target's circle. 6) If it fails, check the exceptions: Equivalent (another control on the same page that meets the criterion does the same job), Inline, User Agent Control (size set by the browser and not modified by the author), Essential. 7) This SC covers pointer input only. Automation: no ACT rule is listed on the page. axe `target-size` (tagged wcag258) checks this. Auditor guidance: automation cannot decide Equivalent, Inline, or Essential, and may mis-measure padding or overlapping hit areas.
- **Fails when:** an undersized target (no 24 by 24 CSS px square fits inside it) has a 24 px diameter circle that intersects another target or another undersized target's circle, and no other exception applies. Examples from the page: menu items only 18 px high stacked in a column fail. Rows of 16 px high buttons stacked 1 px apart fail. 20 by 20 px buttons with no gap fail (a 4 px gap passes). A 16 by 16 target touching a large target fails (a 4 px gap passes). An author-modified scrollbar with no space to an adjacent link fails. Zoom does not fix a failure: the CSS pixel size does not change when users zoom.
- **Does not fail:** targets of at least 24 by 24 CSS px need no extra spacing. A small target with enough clearance passes, for example 16 px high buttons with no target directly above or below. Targets in a sentence, or whose size is constrained by the line height of non-target text (Inline). A browser control whose default size the author did not modify, such as the days in `input type="date"` (User Agent Control). A different control on the same page that does the same job and meets the criterion (Equivalent). Presentations where size and spacing are fundamental to the information, such as map pins, dense data visualizations, or sizes a jurisdiction legally requires (Essential). Targets while they are obscured by content shown as a result of a user interaction or script (combobox list, modal dialog, cookie banner); the new content on top is still tested. When targets overlap, the overlapping area is not counted in the size, unless they perform the same action or open the same page. Keyboard and other non-pointer input are outside this SC.
- **Rate it:** by impact. The audit template treats a computed target size that fails a numeric threshold as High confidence. Severity is not on the confirmed anchors. Auditor guidance: Moderate by default, higher by impact if the undersized control is the only way to do a key task.
- **Source:** https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html (read 2026-10-07).

### 4.1.2 Name, Role, Value (A)
- **Applies when:** Every user interface component: form elements, links, and components generated by scripts. It matters most for custom controls and for elements scripted to act differently than usual, such as a link used as a button. The page says standard HTML controls already meet the SC when used according to specification.
- **Test:** 1. Tab to each control and read its name and role from the accessibility tree (Playwright `ariaSnapshot()`, DevTools Accessibility pane). 2. Operate it with the keyboard and re-read the tree after each change. The page names these states: focus, selected, checked, expanded or collapsed. Auditor guidance: also check pressed, invalid, disabled, and the current value. 3. Check that the focus state can be determined and that changes are exposed. 4. Check that each part of a multi-part field (for example a phone number split into inputs) has its own name. 5. Auditor guidance: check that script-built controls are not plain `div` or `span` elements with only click handlers. axe rules that matter for a component audit: `button-name`, `input-button-name`, `link-name`, `label`, `select-name`, `aria-input-field-name`, `aria-command-name`, `aria-toggle-field-name`, `aria-roles`, `aria-required-attr`, `aria-allowed-attr`, `aria-valid-attr-value`, `nested-interactive`. ACT rules on the page's Test Rules section include "Button has non-empty accessible name", "Link has non-empty accessible name", "Form field has non-empty accessible name", "Element with role attribute has required states and properties", and "Role attribute has valid value". No automated rule checks that a state stays in sync after interaction, that a role matches the real behavior, or that a custom control notifies assistive technology of changes. Test those by hand.
- **Fails when:** The name or role of a component cannot be programmatically determined, a user-settable state, property, or value cannot be programmatically set, or notification of changes to these is not available to assistive technology. Failures listed on the page: F59 (script makes a div or span a control without a role), F15 (custom control does not use an accessibility API, or does so incompletely), F20 (text alternative not updated when non-text content changes), F42 (emulated link), F68 (control has no programmatically determined name), F79 (focus state not programmatically determinable or no notification of focus change), F86 (parts of a multi-part field have no names), F89 (image-only link has no accessible name), F111 (visible label text but no accessible name).
- **Does not fail:** Standard HTML controls already meet the SC when used according to specification. Names may be visible or invisible, and `aria-label` is a listed sufficient technique (ARIA14). What roles and states are appropriate depends on what the control represents. The page notes that accessibility support in assistive technology is a further factor. Auditor guidance: the page gives no list of things that do not fail, and its In Brief says to give components correct names, so do not pass a non-empty but wrong name on this SC alone; report it and note which other criterion covers it.
- **Rate it:** An unnamed focusable control is Critical. A custom control with no role or no exposed state: by impact (higher if a screen reader user cannot tell what the control is or do anything with it, lower if the name and role are right and only a state is stale).
- **Source:** https://www.w3.org/WAI/WCAG22/Understanding/name-role-value.html (read 2026-10-07).

### 4.1.3 Status Messages (AA)
- **Applies when:** In content implemented using markup languages, new content appears or changes without a change of context (no new window, no focus move, no new page) and tells the user about the success or results of an action, the waiting state of an application, the progress of a process, or the existence of errors. Page examples: "5 results returned", "5 items" near a cart icon, "Invalid entry" above an input, a busy icon, a progress bar, "Your form was successfully submitted.", "5 errors on page", and a "Saved in 'Wedding' album" popup.
- **Test:** 1. Trigger each action (search, add to cart, submit with errors, submit with success, start a long process, enter an invalid value). 2. Auditor guidance: run `node <skill folder>/scripts/live-region-probe.mjs <page> --click <selector>` on a freshly loaded page, once per action (add `--ax` for Chromium's view of live nodes). A look at the DOM by hand misses text that is added and removed within milliseconds, which is how a shared announcer works. For each text change the probe reports the live region it landed in (`aria-live`, `role=status`, `role=alert`, `role=log`), whether that region existed before and is exposed to assistive technology (not `display:none` or `aria-hidden`), how long the text stayed, and whether focus moved. It also sees regions inside shadow roots. 3. If focus moved to another element, it is a change of context and out of scope. 4. Decide whether the change is a status message at all (see Does not fail). 5. Class it by the probe result, see Rate it. 6. The page lists these techniques: `role=status` (ARIA22), `role=alert` or live regions for errors (ARIA19), `role=log` (ARIA23), and a live region for a progress bar (ARIA25). It also says other programmatically determinable routes count, including direct access to accessibility APIs. 7. Check changed status text (for example "0 items" to "3 items") and removed status text, such as a "busy" message that disappears. The page says non-sighted users are unaware of the removal unless a non-visible message such as "system available" is provided. 8. Look for a focused button whose inner text changes to show a state or result (for example "Archive" to "Undo archive"). Some screen readers don't announce inner text changes (maintainer decision, C-021). It is a Best practice. If that text change is the only way the user learns the outcome of an action, with no live region and no focus move, also put it under Needs verification with the check (a screen reader on the target browser). A toggle that only shows its own state stays a Best practice. 9. The page lists no ACT rules, and no axe rule proves a message is announced. The probe shows what the browser exposes. It can't show that a screen reader speaks the text, so anything it can't settle goes under Needs verification.
- **Fails when:** A status message cannot be programmatically determined through role or properties (F103). The page also lists a second failure, marked as a future link: using `role="alert"` or `aria-live="assertive"` on content which is not important and time-sensitive.
- **Does not fail:** A list of search results is not a status message. Brief text about the search such as "Searching...", "18 results returned", or "No results returned" is, if it does not take focus or cause a page refresh. A message in a dialog that takes focus is a change of context and out of scope. Content exposed or hidden by expanding a menu, select, accordion, or tree, or by selecting a tab, is not a status message; 4.1.2 covers the state change. New survey questions added after an answer are not a status message; the page calls a message about them a best practice, not a requirement. The page says the purpose of the SC is not to force authors to create new status messages. Auditor guidance: a message that moves focus (for example to an error summary) needs no extra announcement, because the page says messages that take focus are already surfaced by assistive technology.
- **Rate it:** By impact. A missing announcement for an error or a result that blocks the task is higher than a missing "saved" confirmation. Auditor guidance, by probe class for something that is a status message: `no-live-region` or `hidden-region` means the message isn't programmatically determinable through role or properties, a failure, High confidence. `present` means no failure was found, Medium confidence, since a screen reader wasn't run. `transient` (text removed or replaced quickly), `inserted-with-text` (the live region was created together with its text) and several changes in one task go under Needs verification, never as a failure: report the measured dwell and name the check to run (for example NVDA with Firefox or Chrome, JAWS with Chrome, VoiceOver with Safari). The page states no minimum time the text must stay and no rule that the region must exist first, so don't invent one.
- **Source:** https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html (read 2026-10-07).
